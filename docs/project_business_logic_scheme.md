# Бізнес-схема проекту

## Призначення документа

Цей файл фіксує узгоджену бізнес-логіку проекту на поточний момент. Документ потрібен як опорна схема для подальшого проєктування домену, application services, UI-флоу та тестів.

---

## 1. Загальна ідея моделі

Проект працює з трьома основними канонічними сутностями бізнесу:

1. **Спостереження (`InterceptionMessage`)** — факт перехоплення / повідомлення.
2. **Профіль військової особи (`MilitaryProfile`)** — канонічна особа, яка може повторно використовуватись у багатьох спостереженнях.
3. **Профіль підрозділу (`DivisionProfile`)** — канонічний підрозділ, який використовується для нормалізації та візуалізації результатів.

Додатково є доменний зв’язок:

- **`DivisionFrequencyAssignment`** — часовий канонічний зв’язок між частотою та профілем підрозділу.

Також є довідники:

- **Довідник дій**
- **Довідник ролей**

Аналітика не є первинним доменом факту. Вона будується поверх збережених спостережень, профілів осіб, профілів підрозділів і зв’язків частот.

---

## 2. Межі доменів

### 2.1. Домен спостережень

Відповідає за фіксацію конкретного факту:

- дата/час
- частота
- текст / примітка
- учасники повідомлення
- невідомі учасники
- локальні вектори командування в межах цього повідомлення
- snapshot-назва підрозділу для зменшення розходжень і збереження історичності

Головний aggregate root:

- `InterceptionMessage`

Внутрішні child-об'єкти:

- `InterceptionParticipant`
- `InterceptionCommandVector`

### 2.2. Домен профілів осіб

Відповідає за канонічну особу:

- позивний
- канонічний підрозділ
- роль
- частоти

Головний aggregate root:

- `MilitaryProfile`

### 2.3. Домен профілів підрозділів

Відповідає за канонічний підрозділ:

- назву підрозділу
- життєвий цикл профілю
- канонічну ідентичність підрозділу

Головний aggregate root:

- `DivisionProfile`

### 2.4. Домен належності частоти підрозділу

Відповідає за правило:

- в один момент часу одна частота може належати лише одному підрозділу
- один підрозділ може мати багато частот
- частота може перейти іншому підрозділу в майбутньому

Основний об'єкт:

- `DivisionFrequencyAssignment`

### 2.5. Аналітичний контур

Не зберігає первинний факт як є, а будує похідні моделі:

- зв'язки між профілями осіб
- стійкі пари та ланцюги
- контури керування
- групи на частоті
- візуалізацію по підрозділу, якщо частота має канонічний підрозділ
- візуалізацію по частоті, якщо канонічний підрозділ відсутній

Аналітика не повинна підміняти собою первинний факт.

## 3. Логіка `MilitaryProfile`

### 3.1. Призначення

`MilitaryProfile` — це канонічна особа, яку система намагається повторно використовувати між різними спостереженнями, щоб уникати дублювання профілів.

### 3.2. Правила полів

На поточний момент зафіксована така філософія:

- **Позивний** — обов'язковий
- **Частота** — обов'язкова
- **Підрозділ** — optional, але у канонічному вигляді через `DivisionProfileId`
- **Роль** — optional

### 3.3. Nullable-логіка

Для optional-полів діє правило:

- `null` = свідомо очистити значення
- `Guid.Empty` для optional id-поля не є валідним значенням, це помилка вводу

### 3.4. Частоти профілю

Частоти профілю моделюються не окремою сутністю, а колекцією значень (`FrequencyCodeVo collection`).

Окрема child-сутність на кшталт `MilitaryProfileFrequency` для домену не потрібна.

### 3.5. Підрозділ профілю

Канонічний підрозділ особи має зберігатися як:

- `DivisionProfileId?`

Тобто `MilitaryProfile` більше не повинен бути носієм raw-тексту підрозділу як головної істини. Raw-підрозділ залишається на рівні спостереження як snapshot.

---

## 4. Логіка `DivisionProfile`

### 4.1. Призначення

`DivisionProfile` — це канонічний профіль підрозділу.

Він відповідає за:

- канонічну назву підрозділу
- ідентичність підрозділу
- стабільну точку для прив'язки частот і профілів осіб
- основу для відображення аналітичних результатів за підрозділом

### 4.2. Що не повинен робити `DivisionProfile`

`DivisionProfile` не повинен бути головним носієм інваріанту частот через простий список `Frequencies`, якщо для частоти діє правило ексклюзивної належності в часі.

Інваріант `частота -> підрозділ` треба моделювати окремо.

---

## 5. Логіка `DivisionFrequencyAssignment`

### 5.1. Призначення

`DivisionFrequencyAssignment` — це канонічний часовий зв'язок між частотою та профілем підрозділу.

Він відповідає на питання:

- якому підрозділу належала частота
- у який період часу
- чи активний цей зв'язок зараз

### 5.2. Головне бізнес-правило

В один момент часу **одна частота може бути активною лише в одному профілі підрозділу**.

Це ключовий інваріант моделі підрозділів.

### 5.3. Причина виділення в окремий об'єкт

Цей зв'язок не слід тримати просто як список частот усередині `DivisionProfile`, тому що:

- один `DivisionProfile` не бачить інші профілі
- унікальність частоти по всій системі не можна надійно захистити в одному профілі
- потрібна часовість для коректного історичного резолву

### 5.4. Сценарій передачі частоти іншому підрозділу

Коли частота переходить іншому підрозділу:

1. поточний assignment закривається
2. створюється новий assignment на новий `DivisionProfile`

Тобто зв'язок не переписується “тихо” на місці без фіксації зміни періоду.

---

## 6. Логіка `InterceptionMessage`

### 6.1. Призначення

`InterceptionMessage` — це агрегат факту спостереження.

Він відповідає за:

- власний зміст повідомлення
- власних учасників
- власні локальні вектори командування
- власну внутрішню цілісність
- snapshot-значення деяких уніфікованих параметрів

### 6.2. Назва підрозділу у спостереженні

`InterceptionMessage.DivisionName` — це:

- не канонічний link
- не `DivisionProfileId`
- а **snapshot-значення**, що відображає введену або підтверджену оператором назву підрозділу на момент запису

Це зроблено для:

- зменшення ризику розходжень
- збереження історичності
- зменшення кількості міжагрегатних зв'язків

### 6.3. Історичний резолв підрозділу

Канонічний історичний резолв підрозділу не виконується через `DivisionProfileId` у `InterceptionMessage`.

Він виконується через:

- `ObservedDate`
- `FrequencyCode`
- історію `DivisionFrequencyAssignment`

Тобто observation лишається легким, а історичність зберігається через окремий часовий зв'язок частоти.

### 6.4. Учасники спостереження

`InterceptionParticipant` — це child-об'єкт агрегату спостереження, а не окремий aggregate root.

Його сенс:

- зафіксувати, хто саме присутній у конкретному повідомленні
- мати посилання на канонічний профіль особи
- зберігати локальний контекст цього факту

### 6.5. Поля учасника

На поточний момент погоджена така бізнес-ідея:

- `MilitaryProfileId` — обов'язковий
- `Callsign` у повідомленні — локальний факт повідомлення
- `DivisionName` у повідомленні — optional локальний snapshot-контекст
- роль на write-side не є окремою первинною істиною в participant, а може підтягуватись із профілю в read/analytics layer

### 6.6. ParentId у child-об'єктах

`ParentId` не потрібен у доменній моделі child-об'єктів.

Такі поля слід залишати на рівні EF mapping, а не домену.

## 7. Matching профілів осіб при створенні спостереження

### 7.1. Головна ідея

При створенні спостереження система повинна намагатися не плодити дублікати профілів осіб.

Тому логіка така:

1. Оператор вводить назву / позивний особи.
2. UI показує можливі збіги по профілях.
3. Серед підказок оператор бачить, наприклад:
   - назву / позивний
   - частоту
   - підрозділ
   - роль
4. Оператор свідомо обирає один із варіантів:
   - **вибрати існуючий профіль**
   - **створити новий профіль**

### 7.2. Хто приймає рішення

Остаточне рішення про match приймає оператор.

Система може підказувати, але не повинна безумовно і мовчки зливати профілі лише за приблизним збігом.

### 7.3. Де живе ця логіка

Це логіка **application service / UI-flow**, а не агрегату `InterceptionMessage`.

Сам агрегат не повинен:

- шукати профілі
- створювати профілі
- визначати дублікати
- працювати з репозиторіями

---

## 8. Підтягування підрозділу за частотою

### 8.1. Головна ідея

На ручному сценарії введення спостереження зручніше вводити **частоту**, а не підрозділ.

Тому бізнес-потік іде так:

1. оператор вводить частоту
2. система шукає активний `DivisionFrequencyAssignment` на момент `ObservedDate`
3. якщо assignment знайдено — система пропонує відповідний `DivisionProfile`
4. оператор підтверджує або відхиляє пропозицію
5. якщо пропозиції немає — оператор може створити новий профіль підрозділу і новий assignment

### 8.2. Що записується в observation

У `InterceptionMessage` пишеться не id підрозділу, а:

- snapshot-назва підрозділу (`DivisionName`)
- або `null`, якщо підрозділ не визначено

### 8.3. Чому це правильно

Такий підхід:

- зменшує зв'язність write model
- не перевантажує `InterceptionMessage`
- лишає історичність через `ObservedDate + FrequencyCode`
- робить UX природним для оператора

---

## 9. Сценарій створення спостереження

### 9.1. Загальний флоу

При збереженні нового спостереження application service діє так:

1. Отримує дані форми.
2. Для частоти намагається знайти активний `DivisionFrequencyAssignment`.
3. Якщо assignment знайдено — пропонує відповідний `DivisionProfile`.
4. Оператор підтверджує або створює новий профіль підрозділу.
5. Обробляються known participants.
6. Для кожного учасника:
   - або береться вже вибраний існуючий `MilitaryProfile`
   - або створюється новий `MilitaryProfile`
7. Після цього створюється агрегат `InterceptionMessage`.
8. У message записуються:
   - frequency
   - snapshot-назва підрозділу
   - текст та інші поля факту
9. У message додаються known participants уже з валідними `MilitaryProfileId`.
10. Після додавання учасників створюються локальні `CommandVector`.
11. Усі зміни зберігаються транзакційно.

### 9.2. Важливий інваріант

Учасник спостереження не повинен існувати як “порожня заготовка” без профілю.

Тобто `InterceptionParticipant` додається в агрегат тільки тоді, коли `MilitaryProfileId` уже визначений.

---

## 10. Логіка редагування після створення спостереження

### 10.1. Головне правило

Після створення спостереження універсальне редагування учасника небажане.

Причина:

- воно змішує правку факту
- правку профілю
- виправлення помилки match
- виправлення локального контексту

### 10.2. Поточна рекомендована модель

Після збереження спостереження базовий сценарій виправлення такий:

- **видалити учасника**
- **додати учасника заново**

Це чистіше, ніж намагатись підтримувати універсальний `UpdateParticipant(...)` для всіх випадків.

### 10.3. Що лишається редагованим окремо

Редагування самого профілю залишається допустимим:

- змінити роль профілю
- змінити підрозділ профілю
- змінити канонічний позивний
- керувати частотами профілю особи
- керувати assignment-ами частот підрозділів

Ці зміни робляться не через `InterceptionMessage`.

---

## 11. Чи повинне редагування учасника оновлювати профіль

### Відповідь

**Ні, звичайне редагування учасника в спостереженні не повинно автоматично оновлювати профіль.**

### Чому

Бо це різні рівні істини:

- `InterceptionMessage` = історичний або локальний факт
- `MilitaryProfile` = канонічна особа

Автоматичне оновлення профілю через локальну правку одного спостереження може:

- зламати інші спостереження
- змінити reused profile під локальну помилку
- приховати факт помилкового резолву профілю

---

## 12. Логіка помилкового match профілю

### 12.1. Суть проблеми

Можлива ситуація:

- оператор створює спостереження
- система або оператор реюзить існуючий профіль особи
- пізніше стає ясно, що match був хибний

### 12.2. Важливий висновок

Це не є звичайним “оновленням учасника”.

Це окремий сценарій:

- **виправлення помилки резолву особи**

### 12.3. Практичний висновок

Якщо reused profile обрано помилково, то:

- **не можна оновлювати reused profile під цей один факт**
- **не можна автоматично переписувати глобальний профіль**

Чистий практичний шлях:

- видалити учасника зі спостереження
- додати його заново з правильним профілем

---

## 13. Вектор командування (`InterceptionCommandVector`)

### 13.1. Що це таке

`InterceptionCommandVector` — це локальний факт взаємодії в межах одного спостереження.

Він описує, хто в межах цього повідомлення:

- дав команду
- отримав команду
- підпорядковувався
- звітував
- контролював

### 13.2. На що він повинен посилатись у домені

У write model вектор командування повинен працювати через:

- `FromParticipantId`
- `ToParticipantId`

а не через `MilitaryProfileId`.

### 13.3. Чому не `MilitaryProfileId`

Бо в межах агрегату `InterceptionMessage` важлива локальна цілісність:

- вектор повинен вказувати на учасників цього повідомлення
- root повинен мати змогу перевірити, що обидва учасники існують
- при видаленні учасника root повинен мати змогу каскадно прибрати пов'язані вектори

### 13.4. Що потрібно для аналітики

Для аналітики в майбутньому важливі зв'язки між профілями осіб, а не лише між локальними учасниками одного повідомлення.

Але це треба будувати як похідну модель:

- беремо `CommandVector`
- знаходимо відповідних `InterceptionParticipant`
- беремо їх `MilitaryProfileId`
- будуємо profile-to-profile зв'язок у read / analytics layer

### 13.5. Висновок

У домені залишаємо:

- `ParticipantId -> ParticipantId`

В аналітиці будуємо:

- `MilitaryProfileId -> MilitaryProfileId`

---

## 14. Видалення учасника і вектори командування

При видаленні учасника зі спостереження пов'язані `CommandVector` повинні видалятися каскадно.

Це необхідно для захисту інваріанта агрегату:

- у повідомленні не повинно залишатись векторів, які посилаються на неіснуючих учасників

---

## 15. Логіка ролі, позивного і підрозділу

### 15.1. Роль

На поточний момент доцільно розглядати роль як властивість `MilitaryProfile`.

Тобто:

- роль визначається у `MilitaryProfile`
- у read model вона підтягується до спостереження

### 15.2. Позивний

Позивний профілю — канонічний.

Позивний у спостереженні — локальний факт повідомлення.

У різних повідомленнях локальне написання або спосіб фіксації позивного може відрізнятись.

### 15.3. Підрозділ

Підрозділ у спостереженні — snapshot.

Підрозділ у профілі особи — канонічне посилання на `DivisionProfile`.

Канонічна прив'язка частоти до підрозділу — `DivisionFrequencyAssignment`.

---

## 16. Аналітична візуалізація

Аналітика будується від:

- частоти
- профілю особи
- вектора директивного керування

### Правило візуалізації

- якщо за частотою на відповідний момент визначений `DivisionProfile`, результат показується **за підрозділом**
- якщо канонічний підрозділ для частоти відсутній, результат показується **за частотою**

Це дозволяє:

- не втрачати інформацію там, де підрозділ ще не визначено
- використовувати підрозділ як головний вузол там, де він уже канонізований

---

## 17. Чому аналітична ієрархія не є окремою доменною сутністю зараз

Поточна логіка показує, що так звана “ієрархія керування” поки не є первинним бізнес-фактом.

Вона виводиться з:

- частоти
- профілів осіб на частоті
- локальних векторів командування
- повторюваності зв'язків
- ваги та напрямку взаємодій
- наявності або відсутності канонічного підрозділу для частоти

Тому зараз правильніше розглядати її як:

- аналітичний граф
- projection
- read model
- похідний результат

а не як окремий aggregate root.

## 18. Підсумкові правила проекту

### Профіль особи

- канонічна особа
- reusable між багатьма спостереженнями
- позивний і частота обов'язкові
- підрозділ і роль optional
- частоти живуть як value collection
- канонічний підрозділ задається через `DivisionProfileId`

### Профіль підрозділу

- канонічний підрозділ
- не є носієм простого списку частот як головного інваріанту
- використовується для нормалізації та візуалізації

### Належність частоти

- моделюється окремо через `DivisionFrequencyAssignment`
- одна частота в один момент часу може належати лише одному підрозділу
- частота може перейти іншому підрозділу через закриття старого і створення нового assignment

### Спостереження

- окремий факт
- містить локальних учасників і локальні вектори взаємодії
- не шукає і не створює профілі самостійно
- містить лише snapshot-назву підрозділу без канонічного id

### Matching

- профіль особи резолвиться через application service / UI-flow
- підрозділ пропонується за частотою
- оператор підтверджує існуючий профіль або створює новий
- система допомагає, але не підміняє рішення оператора

### Після save

- глобальне редагування participant небажане
- базовий механізм виправлення: remove + add
- профіль особи редагується окремо
- профіль підрозділу і assignment-частот редагуються окремо

### Вектор командування

- у домені посилається на local participant id
- в аналітиці перетворюється на profile-to-profile link

### Аналітика

- працює поверх фактів
- не підміняє собою домен первинного збереження
- стартує від частоти
- показує результат за підрозділом, якщо підрозділ канонічно визначений
- інакше показує результат за частотою

## 19. Напрямок для тестів

З цього документа випливають такі ключові перевірки:

1. Створення спостереження з reuse existing `MilitaryProfile`.
2. Створення спостереження з create new `MilitaryProfile`.
3. Заборона порожнього профілю у known participant.
4. Каскадне видалення командних векторів при видаленні учасника.
5. Відсутність автоматичного оновлення reused profile через локальну правку спостереження.
6. Коректне читання ролі профілю у read model спостереження.
7. Побудова аналітичного profile-to-profile link із локальних participant-based vector.
8. Пошук підрозділу за частотою на момент `ObservedDate`.
9. Неможливість існування двох активних assignment для однієї частоти.
10. Історичний резолв підрозділу через `ObservedDate + FrequencyCode`.
